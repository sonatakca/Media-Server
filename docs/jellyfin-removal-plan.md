# Jellyfin Removal Plan

_Last updated: 2026-07-24_

## Purpose and invariants

Seyirlik will replace Jellyfin with a Seyirlik-owned, versioned API rooted at `/ownAPI/v1/` while preserving the existing React UI, routes, responsive presentation, player controls, and visible user flows. The migration is incremental: Jellyfin remains a development-only reference/fallback until each native slice passes its documented gate. The final removal phase deletes every runtime fallback.

No migration step may mutate or delete Jellyfin data. No step may expose media filesystem paths, credentials, session tokens, FFmpeg command secrets, or internal stack traces.

## Current architecture (repository evidence)

### Frontend

- Vite 6 + React 18 + TypeScript 5 (`package.json`, `vite.config.ts`).
- React Router 6; Tailwind/PostCSS plus component/global CSS.
- PWA generated by `vite-plugin-pwa`; Workbox currently denies Jellyfin API/media paths (`vite.config.ts:49-70`).
- Browser code calls Jellyfin directly through `src/lib/jellyfinApi.ts` and SyncPlay modules under `src/features/partyWatch/`.
- Jellyfin server URL and access token are stored in `localStorage` by `src/lib/authStorage.ts`.
- Admin/developer pages use Firebase Google authentication separately from media-user authentication.

### Backend

- No third-party backend framework is present.
- An optional TypeScript/Node `node:http` modular playback backend is started by `npm run playback:backend` (`src/server/playbackBackend.ts`).
- Existing backend responsibilities: trusted media-root resolution, ffprobe analysis, playback planning, HTTP range delivery, bounded FFmpeg HLS sessions, idle cleanup, Firebase-admin authorization for TMDB artwork, and TMDB artwork sidecar writes.
- The production static Vercel configuration only builds `dist` and rewrites application routes to `index.html`; it does not host the Node media backend (`vercel.json`). A native media server therefore needs a persistent self-hosted process near the media storage and a reverse proxy rule for `/ownAPI/v1/`.

### Database

- PostgreSQL persistence, checksum-tracked versioned SQL migrations, a bounded pool, transaction helpers, and typed native user/session repositories now exist behind the explicit native identity provider.
- Startup validates connectivity and the applied identity schema when native identity is enabled. `npm run db:migrate` remains the explicit, repeatable migration command.
- Media analysis is cached only in memory (`src/server/analysisCache.ts`).
- Browser preferences/auth state are predominantly local storage.

### Caching

- In-memory ffprobe analysis cache keyed by media ID, file size, and modification time.
- Browser-side capability cache and in-flight playback-request deduplication.
- TMDB/network caching is not a general persistent catalogue cache.

### Jobs and scheduling

- No durable queue or scheduler is present.
- A Node interval cleans idle playback sessions.
- Jellyfin currently owns library scans, metadata refresh, trickplay, and scheduled server tasks.

### WebSockets

- No native server WebSocket implementation is present.
- The party-watch feature connects directly to Jellyfin `/socket` with a query-string token and uses Jellyfin SyncPlay REST endpoints.

### Docker and deployment

- No Dockerfile or Compose file exists in the repository.
- Frontend deployment is static Vercel.
- No Nginx, Caddy, Traefik, or other reverse-proxy configuration exists in the repository.

## Target architecture

Use a **TypeScript modular monolith** that evolves the existing Node backend rather than replacing the frontend or creating microservices:

- One HTTP API process serving `/ownAPI/v1/` and media responses.
- One separately runnable worker entry point loading the same domain/application modules.
- PostgreSQL as the durable source of truth for users, sessions, catalogue, jobs, playback state, metadata, settings, activity, and SyncPlay state. It also provides the initial durable job lease/queue so Redis is not required for correctness.
- Redis remains optional for later fan-out/rate-limit acceleration. Native readiness must report it as `disabled`, not failed, when it is not configured.
- Local or mounted generated storage for cached artwork, subtitles, trickplay, and HLS working files.
- FFmpeg/ffprobe invoked through validated argument arrays only.
- Relative browser API URLs (`/ownAPI/v1/...`) behind the production reverse proxy.

The existing raw `node:http` server can host the first native foundation without a framework migration. Before catalogue/auth breadth grows, route dispatch, middleware, validation, and shutdown logic must be centralized under `src/server/ownApi/`. A later adoption of a small HTTP framework requires a separate evidence-based decision and characterization tests; it is not required for the first slice.

## Jellyfin integration entry points

1. `src/lib/authStorage.ts`: server URL, local access-token persistence, Jellyfin authorization headers.
2. `src/lib/jellyfinApi.ts`: authentication, users, libraries, catalogue, state, metadata refresh/editing, playback info/URLs, images, trickplay, sessions, progress, transcode stop.
3. `src/lib/types.ts`: Jellyfin DTOs are the de facto component view models.
4. `src/features/partyWatch/jellyfinSyncPlayApi.ts` and `jellyfinSyncPlaySocket.ts`: SyncPlay REST/WebSocket.
5. `src/server/jellyfinMediaResolver.ts`: backend API-key lookup of item filesystem paths.
6. `src/server/tmdbArtwork.ts`: Jellyfin item lookup/path/provider-ID dependency before TMDB sidecar operations.
7. `src/server/playbackBackend.ts`: requires Jellyfin URL/API key at environment startup and probes Jellyfin diagnostics.
8. `vite.config.ts`, `README.md`, `docs/`, `src/vite-env.d.ts`, translations, and setup/error screens: Jellyfin paths/configuration and user-facing assumptions.
9. Existing built `dist/` and `public/assets/` bundles contain generated copies of the current integration and must be rebuilt only after source migration; they are not source of truth.

The detailed call/field/screen inventory is maintained in `docs/jellyfin-parity-matrix.md`.

## Migration phases and gates

1. **Inventory and contracts** — freeze observable UI/API assumptions; record baseline failures and all dependencies.
2. **API foundation — implemented and verified 2026-07-23** — `/ownAPI/v1/health`, bounded dependency-aware readiness, strict end-to-end request correlation, route-template-only structured logging, default-deny authorization seam, production same-origin CORS with an explicit trusted proxy-origin setting, typed browser client, and graceful shutdown integration. The configured ffprobe and generated-storage paths now drive both health reporting and the corresponding playback runtime. Readiness remains false until both database and durable jobs are available.
   - **Implemented next product-facing slice:** app-bootstrap reachability can switch from Jellyfin's public-system probe to runtime-validated `/ownAPI/v1/health` with `VITE_SERVER_BOOTSTRAP_PROVIDER=own-api`. The explicit adapter has no hidden fallback, accepts `alive: true` while durable jobs are intentionally disabled, keeps retries/diagnostics on the selected provider, and retains `jellyfin` as the default rollback. Vite proxies `/ownAPI/*` to the local backend and the service worker excludes it from navigation fallback. Native identity infrastructure now exists, but production identity traffic remains deferred until `/ownAPI/v1/*` is routed to the persistent backend and a native post-login catalogue slice exists.
3. **Authentication/users foundation — implemented behind explicit flags 2026-07-24** — PostgreSQL users and opaque sessions, Argon2id credentials, one-time first-administrator provisioning, atomic rotation/reuse revocation, signed session-bound CSRF, strict mutation origins, bounded process-local rate limits, cookie security, runtime-validated native `/auth/me` bootstrap, and database readiness. Jellyfin remains the default provider; the existing Jellyfin login UI and all post-login library access remain active. Gate for production cutover is still open because Vercel does not route `/ownAPI/v1/*` to the persistent Node backend.
   - The Vercel configuration now reserves `/ownAPI/v1/*` ahead of the SPA rewrite and returns correlated JSON `503 PRODUCTION_ROUTING_UNAVAILABLE`. This is an honest guard, not an authentication backend. Replace that guard with a confirmed same-origin reverse proxy to the persistent process before setting either identity provider flag to native in production.
4. **Libraries/catalogue schema** — logical items separated from files, permissions enforced in repositories and endpoints.
5. **Durable jobs + scanner** — idempotent reconciliation and file-state grace periods.
6. **ffprobe inventory** — persistent normalized technical streams/chapters/attachments, keyed by source fingerprint.
7. **TMDB metadata/images** — backend-only credential, persistent cache, field locks, safe native image delivery.
8. **User media state** — progress sequencing, watched/favourites, continue watching and next-up.
9. **Playback plan** — deterministic native `DIRECT_PLAY`, `REMUX`, `DIRECT_STREAM`, `TRANSCODE` DTO and exhaustive planner tests.
10. **Authorized delivery/transcoding** — session-bound range delivery and typed FFmpeg lifecycle under native routes.
11. **Tracks/subtitles/chapters** — selection persistence, extraction/conversion/burn-in.
12. **Tasks/trickplay/activity/settings** — durable schedules, sprite generation, operational dashboards, settings precedence.
13. **Native SyncPlay** — authenticated authoritative WebSocket/REST only after single-user playback is stable.
14. **Frontend cutover** — one typed own-API client; preserve DOM/layout/CSS/component hierarchy.
15. **Data migration** — inspect/dry-run/run/verify utilities; source remains read-only.
16. **Jellyfin-disabled soak** — full functional, playback, security, performance, restart, and failure testing with Jellyfin stopped.
17. **Final removal** — remove clients, DTO names, config, fallback, generated bundles, and obsolete tests; zero-dependency audit.

Each phase must update `docs/jellyfin-removal-verification.md` before the next begins.

## Data-migration strategy

- Add an idempotent import ledger containing source kind, source identifier, target identifier, source fingerprint, migration version, status, and discrepancy details.
- Provide `inspect`, `dry-run`, `run`, and `verify` commands.
- Read Jellyfin through a dedicated migration adapter or exported JSON only; never write to its database/API.
- Import users without password hashes unless hash format/parameters are independently validated; require native password setup/reset.
- Map libraries and items by stable source ID plus provider IDs and normalized file fingerprints.
- Import watched state, play count, position, favourites, and preferences after catalogue identity is verified.
- Compare counts and coverage for users/libraries/media hierarchy/provider IDs/state/available files. Unmapped records remain reported, not silently dropped.

## Development rollback strategy

Rollback during development is a **routing/feature-flag rollback**, not a destructive Git or data rollback:

- Native and Jellyfin adapters coexist behind explicit per-domain feature flags while a slice is under verification.
- Dual-read comparison may be used in non-production diagnostics; do not dual-write user state unless idempotency and conflict policy are defined.
- Native database migrations are forward-only in shared environments; local test databases are disposable.
- Before a cutover, preserve a database backup and the discrepancy report.
- If a native slice fails its gate, route that slice back to the unchanged Jellyfin adapter and retain native data for diagnosis.
- After final acceptance, all runtime flags and fallback code are deleted. Historical migration tools/docs may remain isolated and non-runtime.

## Final removal criteria

Jellyfin removal may start only after all parity rows are native and verified, the complete test/build/security/playback gates pass, and Seyirlik operates with Jellyfin stopped. Final source/config/package/deployment searches must prove no runtime references to Jellyfin, `8096`, `8920`, Jellyfin headers/tokens, DTO names, playback routes, or SyncPlay remain. Remaining references must be limited to historical documentation or intentionally isolated migration fixtures/utilities.
